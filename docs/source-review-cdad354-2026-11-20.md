# Anonymum v0.7 contact privacy and handshake review

> **Provenance.** Produced by an AI system (ChatGPT) on 2026-11-20 at the owner's request. It is not an independent human cryptographic audit, and says so itself. Findings 1, 3 (that keys are accepted unvalidated) and 4 were confirmed against the code by a second AI system; the rest is unverified.


**20 November 2026 · Reviewed tip `cdad35413d9791be5a19c84bb21ae6fbf6974699` · Baseline `af61c8f`**

**Disposition.** Keep Noise IK for the prototype. The normal listener now authenticates and authorizes a fresh caller before writing its first reply. An unauthorized stranger with the right public card and route no longer gets the old XX wallet credential. Keep the production responder-privacy and first-contact admission findings open. Revocation, loss recovery, imported key validation and the binding to an actual finalized payment still need work. This is an AI-assisted defensive source review of three commits, not an independent human cryptographic audit. ## Answers to the eight review questions

### 1. Is permission checked before any byte is sent?

**For a newly initiated, unauthorized call through the normal responder, yes at the application layer. For every exported or cached path, no.** Replacing XX removed the wallet credential from the early reply. In IK, successful opening of HELLO yields the caller’s static public key and the encrypted request reference. It authenticates the origin of that flight under the key assumptions. It does not distinguish the live caller from somebody replaying its prior packet. V0.7 explicitly acknowledges that limitation while also using the stronger phrase “controls a key” before replying. ### 4. Note authenticity, forwarding and third-party disclosure

The codec signs a domain label, admission value, intended inbox public key and the full encoded body including sender contact key, callback key, route, version, length and padded intro. The signature is inside the Noise N ciphertext. The decoder’s Rust argument is a complete contact identity, but the decryption path uses only its inbox key and the public prefix. An inbox-only scanning interface could reflect that narrower authority. It opens the note and verifies Ed25519 strictly against the named signing key. This prevents changing the named sender, callback, route or destination while retaining the same honest signature. It does not authenticate the legal identity of a key holder, ownership of a purported wallet, or the origin of a substituted self-signed card. Pin the contact key through the intended invitation/card distribution process. There are three different meanings of “forward.” Re-addressing a signed body to a different inbox fails verification. Copying the entire original field into another transaction for the **same inbox** remains possible until independent admission binding exists. Showing opened contents and their intact signature to another person is intentionally possible with Ed25519. The evidence attests to a key signing a particular statement for an inbox and admission value; it does not independently attest to delivery, the payer, a finalized acceptance or a signing time. Also, the signed card binds a network, whereas the note signature and Noise N prologue contain no network or pool ID. Reusing an inbox key across networks allows the same field to remain valid in the other context unless the application independently scopes it. ### 5. The callback key

Carol creates a fresh callback key for her throwaway listener. Bob initiates using the stable handshake key published on his contact card. An authorized Carol can identify Bob by design. Colluding recipients of calls can compare that static key across requests. Under later compromise of Carol’s callback private key, a recorder of Bob’s first flight can recover Bob’s static public key and the reference. The same reference in the ledger identifies the note or its copies. That exceeds the privacy loss of merely recognizing a returning caller. No compromise of Bob’s spending key is required; the effect does not by itself decrypt subsequent ordinary transport messages. Exchanging long-lived routes later intentionally lets each counterparty retain those routes. The development keep file contains the callback secret in plaintext. ### 6. Confirmation and disagreement between the two sides

The two IK messages establish keys. The caller’s encrypted CONFIRM gives the responder evidence of current possession of fresh transport keys before the invitation is consumed. The responder's ACK, or successfully opened responder DATA in the current code, tells the caller the session is usable. CONFIRM and ACK are **application transport records**, outside the two Noise IK handshake messages. Dropping a failed-to-decrypt CONFIRM without terminating pending state is reasonable under Noise transport semantics. The same grant must still be authorized when a valid CONFIRM eventually arrives. [wire.rs:318](https://github.com/mulasticanon/anonymum/blob/cdad35413d9791be5a19c84bb21ae6fbf6974699/crates/crypto/src/wire.rs#L318) [wire.rs:328](https://github.com/mulasticanon/anonymum/blob/cdad35413d9791be5a19c84bb21ae6fbf6974699/crates/crypto/src/wire.rs#L328) [wire.rs:491](https://github.com/mulasticanon/anonymum/blob/cdad35413d9791be5a19c84bb21ae6fbf6974699/crates/crypto/src/wire.rs#L491) [Noise §5, 11 July 2018](https://noiseprotocol.org/noise.html#processing-rules)

| Delivery state | Responder | Caller |
|---|---|---|
| All CONFIRMs lost | Pending. No grant committed. Eligible for pending expiry if the driver runs its timer. | Can resend, restart, then give up. |
| A valid CONFIRM arrives, all ACKs and qualifying DATA lost | Grant committed locally, invitation honored if applicable, transport live. No live-session expiry is implemented. | Can exhaust attempts with no evidence that the responder committed. |
| ACK lost, exact attempt still current | Library can resend the exact cached ACK if the CONFIRM is delivered again and the responder keeps reading. | Can establish on the retransmission. The current demo driver may already have stopped reading. |
| Caller advances to a higher attempt on the same reply handle and call ID | Can send WELCOME for the new attempt, yet reject the matching CONFIRM in the older live-entry branch. | Retry can fail despite healthy subsequent delivery. |

No finite sequence of acknowledgements makes both devices simultaneously certain under arbitrary final-message loss. The engineering goal is idempotent grant commitment and eventual convergence after communication resumes. Expose “authorized locally”, “peer confirmed”, and “expired” as appropriate; integrate recovery from asymmetric state and continue driving the receive loop. Responding to a duplicate must never reactivate a revoked transport.
