## 1. Decision for the project owner

**The single-nullifier escrow is viable enough to implement.** The reference model uses the same escrow marker for all outcomes, checks separate spending authorities, enforces a rounded-up 1% penalty and constrains the exact refund. A recipient who knows the escrow seed can recognize the settlement and whether the deterministic refund appeared. Keeping its *subsequent spend* hidden depends on a separate, owner-bound ordinary nullifier secret and a privacy-preserving authorization scheme. The project does not yet have a proof circuit establishing those properties.

**The most immediate money issue is wallet recovery.** The model derives refund keys for a `u64` index but its recovery lookup tries only indices 0–999. Its encrypted self-copy records the escrow, not the role key indices needed for direct derivation. Its refund finder also scans for the expected commitment without first proving that the same finalized transaction consumed that escrow. Fix these now, while a changed recovery format costs test coins. The current 101-unit test passes because it uses a recoverable low index; it does not demonstrate recovery for the rest of the API's domain. [Wallet source, pinned commit](https://github.com/mulasticanon/anonymum/blob/38e759f5fa8543008a1ff27080ee8206d1780938/crates/shielded-model/src/wallet.rs#L100) · [Acceptance fixture](https://github.com/mulasticanon/anonymum/blob/38e759f5fa8543008a1ff27080ee8206d1780938/crates/shielded-model/tests/acceptance_5b.rs)

**The most immediate anonymity issue is the transition from transparent contact identity.** The XX responder sends its reusable account-address credential before approving the initiator. The sealed-note decoder needs the stranger's sender address before decryption, and the demo gets it from a transparent chain event. A production wallet that reproduced those interfaces would give peers or infrastructure identifying information even with perfect payment proofs. The first XX packet does carry an empty payload, and the implementation authenticates received transport messages before advancing the replay window. Preserve those controls during the redesign. [Noise session code](https://github.com/mulasticanon/anonymum/blob/38e759f5fa8543008a1ff27080ee8206d1780938/crates/crypto/src/session.rs) · [Sealed notes](https://github.com/mulasticanon/anonymum/blob/38e759f5fa8543008a1ff27080ee8206d1780938/crates/crypto/src/note.rs) · [Mixnet integration](https://github.com/mulasticanon/anonymum/blob/38e759f5fa8543008a1ff27080ee8206d1780938/crates/nym/src/main.rs#L291)

**Keep the public fee fixed under the current owner-approved rules.** I8 is real for both increases **and decreases**. For a new design, §5 recommends allowing a funded ceiling and privately returning the unused reserve on every settlement. This would change owner decision O7 and requires the owner's explicit choice before implementation. It leaves the recipient's price and the 1% penalty alone. There is no way to promise arbitrary future fee increases, a full payout, an offline/empty-wallet sender and no external funding all at once.

**Can the proof be lighter?** Yes. The ledger must enforce who can spend, what each permitted outcome pays, and which funds are retired. The recipient can check its invitation, quote and decrypted opening locally before displaying a request. That saves proving work at a concrete price: a sender can fund an unreadable escrow, and an offline sender must recover a compulsory refund using its backup and finalized history alone. Test that recovery before choosing a faster hash. For the first phone benchmark, use one full Groth16 circuit with the same public shape for payments and escrow actions. The strongest argument against this route is that the team assumes responsibility for a new value-conservation circuit and its trusted setup. A successful audit of the library does not settle either responsibility. There is no timing result for this circuit yet.

### Answers to the ten questions in the source

| Spec question | Design judgment and condition |
|---|---|
| 1. Shared escrow seed (S:363) | Viable. Use a fresh, private, high-entropy seed, bound by the escrow commitment and recoverable by both sides. Every resolution proves the same marker from this seed, the immutable note identity and its authenticated position. Grant each role separate authorization. Knowing the seed must give neither party an additional spending role. Root, branch, current schedule and current circuit version must not change a live note's marker. |
| 2. What the sender learns (S:365) | On complete finalized history, the sender learns the resolution transaction and time. The sender can compare its outputs against the deterministic refund marker, in this case the **refund note commitment**. Under a precise and exclusive output relation this generally distinguishes claim from refund. The common nullifier by itself only signals consumption. Parties also know which actions they themselves submitted. Do not promise privacy against a counterparty that can disclose or prove its own opening. |
| 3. Leaf time and public windows (S:367) | The grid in S:102–108 and S:207 now gives a clean last valid cell. Expiry is measured from the start of the inclusion cell. A funding near its end loses almost one cell of wall-clock opportunity to claim. Require the inclusion state's consensus clock, an accepted anchor, current spent set, and canonical immediate or future scheduling policy. All envelopes reveal execution windows. Near-deadline traffic, retries and low volume can still narrow the likely opening. |
| 4. Reserve linkage (S:369) | A private, properly blinded reserve held inside the same escrow, with no extra public field, need not directly link the two spends. Publicly differing fee credits, old verifier selectors, exceptional calls, events or late wallet fetches can reintroduce a link. A counterparty already recognizes its shared marker. |

Blinded, zero-retirement outputs at S:225 avoid a distinguishable missing slot only if their bytes follow the real distribution. |
| 6. Fixed public base split (S:372) | Feasible if each comparable envelope pays the same public split from shielded value, with no outer payer identity or action-specific side accounting. The public operator recipient and deliberately public payouts are disclosed exceptions. | 7. Proof system (S:374) | Test the single reviewed-library BLS12-381 Groth16 route first, keeping the circuit-specific ceremony and new circuit within audit scope. | 8. Knowing the refund (S:376) | S:132–134 and S:231–237 now specify the blinding exception and original escrow position. Both principals can recognize the refund commitment. ### Additional findings to close before freezing the circuit

- **High, conditional on implementation — receipt semantics.** S:147–152 and S:246–251 bind a recipient, digest, tier and same-envelope escrow. Define the request digest's exact preimage, including a fresh request ID, authenticated initiator/session binding where applicable, and a domain that prevents cross-network use. Compare the escrow's actual resolution authority and payout information to the one recognized by the receiving wallet. Scope `stranger` to the Open branch: a decline at price `100 × S` also burns exactly `S` but must never produce a stranger-tier receipt (S:304–306). Match one finalized envelope and slot, apply idempotent wallet admission and define cross-device one-time-invite semantics. A cryptographically valid receipt can otherwise be counted twice by unsynchronized applications.
- **High for privacy if the cover profile is distinguishable.** Fresh blinding is specified for monetary notes. Empty admission records are separate objects, outside the tree (S:147–152). Require fresh secret blinding and the same public encoding/distribution for real and empty admissions, dummy serials, note types and cover ciphertexts. Domain-separation tags belong inside pseudorandom serial derivations. Exposed type bits, recognizable fixed dummy records or noncanonical random bytes undo the common envelope. The S:309 dummy-marker property is computational: an adversary should succeed only with negligible probability, not literally be unable to produce a colliding string.
- **Medium — what admission assures.** S:267–276 applies to a still-unspent, synchronized, in-window **stranger** opening. Invited requests intentionally have no escrow (S:205). Receipt display is pending until the correct claim finalizes. A recipient decline is authorized by the recipient. Here “sender’s authorisation” must denote the transaction’s acting authorizer, never require the original funder online. An authorized, unusable opening can still consume recipient resources and a deadline opportunity. Refuse to render free-text or confer paid acceptance solely from a syntactically valid receipt. A relayer's unauthorized byte changes must invalidate the envelope.
- **Low — small refund semantics.** Prepaying the resolution fee lets a holder settle an eligible escrow without a second money input (S:78–81). A later ordinary spend has its own fee. At price one the refund is zero. A positive refund below the transfer fee may need another input for a subsequent economic spend. Test these boundary cases separately from the 101-unit example at S:338–347.
- **Editorial issue tracking.** S:11–13 says I1–I12 were resolved, although I8 remains open. I:22–23 labels I13 and I14 open. S:132–134 already implements the proposed I13 wording while its cryptographic question remains, and S:32,72–75 already implements the I14 wording. Close I14 in the issue register and distinguish the textual I13 correction from the unresolved cryptographic instantiation.

## 3. Escrow and admission security

**Assessment, 19 November 2026.** The v0.5 specification and rules model describe a plausible construction. The following are proposed acceptance conditions. Neither a plain-Rust rules model nor an equality between two example values establishes them for a future circuit. The Zcash specification distinguishes note ownership, nullifier derivation, and spend authorization. Penumbra’s claim proof is a precedent for deriving a positioned nullifier and constraining the resulting output commitments. Its one-party swap claim does not provide a security proof for this two-party escrow. [Zcash Protocol Specification, 19 Nov 2026, §§3–4](https://zips.z.cash/protocol/protocol.pdf) · [Penumbra SwapClaim, inspected 19 Nov 2026](https://protocol.penumbra.zone/main/dex/action/swap_claim.html)

**Serial and authority.** Commit the private escrow seed, exact price and fee entitlement, refund receiver, claim receiver, the two scoped resolution authorities and complete request context to a typed hiding escrow commitment `C`. Authenticate the leaf at position `i` under a permitted root. All permitted resolutions must produce the same `N_e = Serial_esc(seed, ledger_domain, C, i)`. These arguments are immutable throughout the note’s life. Transfer of authority, signing key selection, branch, time, root and current verifier version must not change the serial. Prove knowledge of the active branch’s separate private authorization material, or a valid authorization tied to the complete effect. Knowing the common seed must never authorize spending. Keep all historical spent markers through upgrades. Use strictly validated, injective encodings and separate domains for ordinary, escrow and dummy derivations. Require computational resistance to chosen-input collisions across the domains. Domain labels alone do not establish a security reduction.

**Refund.** The proof recomputes the *entire* refund note, including its type, asset, the original sender’s committed refund descriptor, value, and all randomness needed for spending. Its randomness must be determined by a reviewed derivation under a dedicated domain from the shared seed and immutable escrow identity, including its authenticated position. No field that affects spendability or discovery may be freely chosen by the party declining. The restored sender identifies the qualifying output in the **same** finalized transaction that consumes `N_e`. It checks the exact commitment, learns the new output position and updates the ordinary-note witness. Merely seeing a commitment of the expected value somewhere in history is insufficient.

Define ordinary spends using an independently owner-bound nullifier key. The ordinary note’s creator and either escrow principal can know its plaintext and blinding without gaining the owner’s ordinary nullifier key or spend authority. **The recipient knows more than “my escrow resolved.”** It can link the opening to the settlement, recognize the deterministic refund and learn its amount and position. Assuming a key-private output format, an unlinkable ordinary spend authorization and an owner-only ordinary nullifier, this knowledge gives no direct public test for the refund’s *later* spend. Metadata, subsequent voluntary disclosure and a compromised wallet remain separate ways to infer it. Exporting a viewing capability with nullifier derivation changes this conclusion. The wallet disclosure must say so.

**Opening and recovery.** Generate a fresh high-entropy escrow seed with the wallet’s reviewed random generator. Deliver it to each participant inside the authenticated escrow opening. A sender self-copy under a separately derived and backed-up outgoing recovery key avoids relying on a device-only log or counters. Bind role, suite, pool and the corresponding commitment and slot in the ciphertext context, without a circular reference to a transaction hash containing itself. On honest funding, locally use the documented restore procedure to decrypt/check the sender self-copy before authorization. The ordinary signing and nullifier secrets never go into either copy. Require recovery after key rotation, device loss, interrupted submission and chain reorganization. A compromised outgoing key reveals the escrow openings in its scope. Publishing the contact card must not convey this power.

**Delivery guarantee.** If ciphertext correctness stays outside the proof, consensus may accept a funded but unreadable opening. An honest recipient admits it only after checking the full decrypted opening against the finalized commitment, its own keys and price, the same-transaction admission receipt and current unspent status. A paid acceptance is provisional until the recipient’s claim finalizes. Fresh payer-chosen note randomness is permissible for ordinary voluntary payments, where a recipient credits only an output it can recover. A compulsory refund cannot depend on fresh secrets chosen by its creator if the absent beneficiary needs those secrets to recover it. Authenticate the exact submitted ciphertext bytes under the spending authorization so a relay cannot alter an honest opening. Sender-authorized garbage and relay corruption have different validity. If the product advertises guaranteed decryptability for *every funded* opening, this weaker profile does not satisfy it. Zcash’s receiver checks establish a precedent for rejecting invalid note plaintexts locally. They do not transfer an escrow recovery guarantee. [ZIP 212, 31 Mar 2019](https://zips.z.cash/zip-0212) · [Zcash effect/authorization digest separation, ZIP 244, 6 Jan 2021](https://zips.z.cash/zip-0244)

## 4. Proposed verifier statement and state transition

These are implementation requirements for the **fixed-base-fee profile**. A variable-fee release requires the separate fee invariant in this review. The notation below specifies relationships. It does not define new cryptographic primitives or final wire encodings.

| Layer | Required checks |
|---|---|
| Public statement | Bind chain and immutable pool identity, active circuit and rules, supported root, one eligible common half-open validity window `[L,U)`, fixed public fee `F`, a fixed number of spent serials and new commitments, a randomized admission commitment, and the authorization inputs for one exact effect. All actions have the same exposed lengths, authorization shape, call, verifier, padding convention and public fee effect. Canonically encode bytes and field elements without silent modular reduction. |

## 5. Fee changes, confidential supply and time

**High, settlement liveness.** An escrow containing principal `P` and exactly the opening day's fee `R` has only `P+R` to distribute. If today's required fee `F_t>R`, the recipient cannot receive the promised `P`, and the chain cannot also collect `F_t`, without another source for the difference. Revealing an old cheaper fee only on settlements discloses a class of transactions. Waiting one day after disabling new escrows does not clear this liability. A sender may remain offline indefinitely with an unclaimed refund. These are accounting consequences of the brief's rules. Penumbra's SwapClaim binds the public claim fee to a prepaid fee in a private opening, a precedent for prepayment with a different observability contract. [Penumbra SwapClaim, Fee Consistency Check, accessed 19 Nov 2026](https://protocol.penumbra.zone/main/dex/action/swap_claim.html)

**Recommended change for a new pool, conditional on the owner amending O7.** Establish a lifetime fee ceiling `C` for this pool and lock exactly `C` in each new escrow in addition to `P`. Allow the common public inclusion fee `F_t` to rise or fall within `[0,C]` under a published, authenticated schedule. Use positive fees if required by economics. On every resolution return the difference `Q=C-F_t` to the committed sender refund destination, including when the recipient claims. The validator enforces the same current fee and publicly credits the same current base-fee split on every user transaction. The circuit binds the input reserve, the active fee and all destinations. The hidden retired amount never appears in a public issuance delta. This redesign refers to reserve `C`, in place of the brief's exact-fee reserve.

| Hidden resolution | Participant outputs | Hidden retirement | Public fee |
|---|---|---:|---:|
| Authorized claim before expiry | `P` to recipient, `Q` to sender | 0 | `F_t` |
| Authorized decline, cancellation or timeout refund | `P-b` to sender, separate `Q` to sender | `b = ceil(P/100)` | `F_t` |

Both rows consume `P+C`. Two participant slots, uniformly shaped recovery data and a blinded retirement slot appear on every action. Constrain the exact expected commitment of **every** output payable to an absent party. The original principal refund remains computable from the opening alone. The separate reserve rebate on every resolution, including claims, needs its own purpose domain distinct from that of the principal note. Its blinding/receiver derivation must use the shared opening, original immutable note identity, a purpose domain and the prescribed public inclusion-fee context. After finding the common nullifier in authenticated history, the restored sender knows the actual `F_t` and can compute the appropriate candidates. It does not depend on a memo from the resolver. Use independent owner-secret ordinary spending/nullifier material. Ensure `P+C` and outputs fit the amount range. Constrain ceiling division without overflowing `P+99`.

**Worked review fixture, in base units.** The sender opens at fee 7 with `P=101` and `C=20`, funding the 121-unit escrow plus the opening fee and applicable surcharge separately. At fee 12 a claim pays 101 to the recipient, 8 to the sender and 12 publicly. A refund pays the sender 99 principal and 8 rebate, retires 2 and pays 12 publicly. At fee 4 the sender receives 99 principal and 16 rebate, with 2 retired and 4 paid publicly. At fee 20 the rebate is zero and the public shape remains the same. Reject a fee of 21. Test all outcomes, downward and upward changes, a stale proof crossing activation and a wiped sender finding the rebate *and* the principal refund without the recipient's cooperation. A fee decrease also requires the rebate rule. Otherwise an implementer must guess who owns the surplus.

**Cost and alternatives.** Every opener ties up `C`, which can price out small senders. Small rebate notes may cost more to spend alone than their face value; include their recovery and later consolidation in tests. Fees beyond `C` require a separately financed or versioned policy. For a valueless pilot, fixing `F` throughout is simpler and satisfies the original model. For arbitrary increases, a private extra input from a sponsor or resolver can fund a deficit, but an offline or empty-wallet user has no guaranteed sponsor. A public subsidy only on recognizable legacy settlements can disclose their class. A subsidy common to all envelopes can hide that distinction if its public accounting is uniform, but depends on a funded budget. None of these choices retrospectively fills an already funded exact-fee escrow. Before activating a repricing with legacy notes, fund and test a migration/compatibility mechanism or maintain a compatible maximum fee. Governance cannot silently increase outstanding reserves. Publish how old spend identities and spent-set entries remain valid.

**Supply bookkeeping.** On a base fee `F_t`, the runtime consumes one private-to-public fee and credits exactly the public burn share plus operator share in the same state transition. Count operator receipts as *live* public value until actually burned or paid. For a direct-issued native coin, the useful gross invariant is private liquid value + escrow principal and reserves + live public value + cumulative public burn + cumulative hidden retirement = gross issuance, subject to explicitly authorized other emissions/exits. This is an analytical invariant. Several terms are deliberately hidden from the public. Exclude a backing vault already represented by shielded notes. Cumulative “public fees paid” ceases to be a separate sink once operators can spend or re-shield those receipts.

The executed finite arithmetic check in §11 covers these proposed equations.

### Consensus time and linkability (brief question A6)

Let `t` be the validated inclusion time and `W` a common window width that divides 86,400 seconds. Stamp every new leaf with the start `L_0` of the **actual inclusion window**, fixed by the runtime. For half-open windows require `L <= t < U`. A recipient claim requires `U <= L_0 + 86,400`. At exactly the deadline a claim is ineligible. Sender early cancel and post-deadline refund have the same destination and penalty, so the sender's refund authority can span the boundary. Advancing a clock confers eligibility. Creating a credit requires a finalized settlement. Authenticate the inclusion clock, monotonicity/skew limits and the note's position and birth stamp. With this rule, “24 hours” means since the start of the opening window. Actual elapsed consensus time from inclusion can be up to almost `W` shorter. State it in the wallet and choose `W` with the owner.

Use common windows and root-selection policies on all actions. Every observed claim-like event narrows candidate openings using public chronology and the adversary's prior information. A rare request resolved almost exactly a day later may be linkable even when nobody publishes its deadline. Measure posterior concentration under actual retries, offline wallets and cancellations. An upper bound on the number of eligible commitments is not an anonymity guarantee.

**Fit to current implementation.** `Chain::submit` checks the rule set and current `F`. The Open and Resolve constraints both require reserve equality to that fee. A lower fee also blocks an old escrow, even when more than enough funds are locked. Three output slots already exist, but both resolution predicates and sender recovery must be revised to service a private rebate. The cheaper alternative listed in specification question 10 is to overfund to `C` and **retire the surplus**. Then every opener economically pays `C` for settlement, even when the published tariff is lower, including on a successful claim. It avoids a rebate note at the price of a new hidden burn distinct from the 1% penalty. A frozen pilot fee is the only option here that requires no change to O7. Old validator versions and extant funded reserves need explicit transition rules. The existing test searches for literal address bytes in frames, which tests only that narrower property. `session.rs:87–95,129–132`; `identity.rs:39–40`; `crypto/tests/crypto.rs:92–104`; `nym/src/main.rs:303–335`; `README.md:99,132`. | Use a contact authority scoped separately from money, existing chain accounts and wallet-wide view keys. Define whether a stranger may learn a publicly listed contact identity merely by reaching a rendezvous endpoint. For peer-private identity release, require authenticated admission before releasing contact-identifying credentials. Bind the accepted request, peer identity, roles, protocol and network to the session using agreed private context and/or a post-handshake transcript confirmation. A final handshake hash belongs after the handshake completes. [Noise rev. 34, 2018-07-11, §§6, 7.8 and 11.2](https://noiseprotocol.org/noise.html) |
| **High — confirmed unknown-sender discovery dependency; migration blocker.** | The existing 427-byte Noise N note requires both wallet addresses as prologue input. The demo obtains `from` from the public request before it decrypts. The crypto test makes the same assumption. A recipient scanning an anonymous chain cannot decrypt this format using only the incoming key and these bytes for a previously unknown sender. The format correctly enforces size, version, intro length, zero padding and UTF-8, but supplies no sender authentication itself. Compromise of the recipient's static secret can expose historical notes given recorded context. `core/src/crypto.rs:61–79`; `crypto/src/note.rs:19–23,71–98,103–130`; `crypto/tests/note.rs:91–116`; `nym/src/main.rs:289–292`. | Use a versioned initial delivery format with pre-decryption context known to a new recipient. Put the claimed initiator identity and authorization inside the receipt-bound contents, or specify and evaluate an outer private delivery mechanism. Test fresh-wallet stranger detection without addresses in clear or targeted lookups. Require key privacy of the complete envelope and test externally observable acceptance behavior. N's documented identity property concerns testing candidate **private keys** and observable acceptance; this finding does not establish recognition from public keys alone. [Noise rev. 34, 2018-07-11, §§6, 7.4 and 7.8](https://noiseprotocol.org/noise.html) |
| **High — confirmed dev-only exposure if used with real keys.** | The CLI explicitly documents and writes both Ed25519 and X25519 private keys as plaintext hex. The demo prints addresses, timing, decrypted introductions or messages at several call sites. These are test facilities; no production use or live compromise was observed. `nym/src/main.rs:155–162,240–261,289–292,442–443,486–505,529–535`. | Exclude the dev wallet/verbose demo commands from release artifacts, require OS-backed encrypted key storage and protected recovery, and verify normal error reports, logs and telemetry contain no secrets or peer graph. |
| **Medium — confirmed retry/state-management defect, with availability implications.** | The initiator consumes the pending handshake before validating flight 2; the responder removes its pending entry before validating flight 3. The demo's retry loop reuses the original first frame and the same initiator object after an error, so a previously consumed state stays unusable. Pending handshakes are capped at 1,024, but the generic responder has no expiry or bounded lifetime/cap for established sessions in the inspected module. Sessions are stored before the caller's admission decision. `wire.rs:84–96,109–123,152–177,189–192`; `nym/src/main.rs:561–584`. | Define clean session restart and expiry after failure, attach authorization before exposing app-message delivery, bound per-peer/global work and sessions, and test a failed handshake followed by a valid retry. Protect the 24-hour payment flow from relying on this UI retry loop. |
| **Medium — confirmed receive-side allocation gap.** | Sending has a size check. Receiving allocates a plaintext buffer sized from an incoming frame after only a minimum-size check. Actual exposure depends on each upstream transport's validated reconstruction cap. `session.rs:175–184,189–203`; `wire.rs:174–177`. | Reject oversized data before any attacker-sized allocation in the public crypto API, and budget pending input/session memory across the transport and application layers. |
| **Medium — confirmed disclosure to counterparties, conditional risk beyond them.** | Ordinary replies use Nym anonymous sender tags, but the reverse-rendezvous demo explicitly exchanges both *long-lived Nym addresses* inside the established encrypted session. It reconnects the stored throwaway client and retries the same first frame on a fixed 150-second schedule, up to three attempts. Calling this endpoint “anonymous to the counterparty” would be inaccurate. A Nym recipient address is not itself an IP address. The timing and retry signals are hypotheses for cross-layer measurement, not a demonstrated network-level identification rate. `nym/src/main.rs:39–44,72–99,349–385,402–424,561–583`. | State exactly which address is exposed and when. Use scoped addresses if cross-contact route linkage is outside the intended leakage. Measure reply, callback, retry and wallet-sync traces with sleep and outage scenarios. |
| **Medium — confirmed migration dependency for one-time invitations.** | The holder receives an exportable Ed25519 signing key. Signatures cover a purpose tag and opener/recipient addresses and are verified strictly; “one-time” consumption in the current design relies on chain state. State whether disconnected devices may accept the same credential before synchronization. In a bearer-invite design voluntary sharing cannot be cryptographically excluded. |

**Transport replay and key lifecycle.** Sending uses exclusive mutable session access and a monotonically increasing counter, incremented only after successful encryption. Receiving authenticates a frame before advancing the high-water mark and inserts accepted counters in a sliding 2,048-value receive set. The in-memory session is neither serializable nor clonable through the reviewed public API. Identity restore reconstructs long-lived keys, and a new handshake starts a new transport. I found no evidence here of automatic counter reset under a surviving transport key. Add tests at the replay-window boundary, at the maximum nonce including the reserved value, on fresh sessions following restarts, and around simultaneous device clones. Check the pinned dependency's nonce-exhaustion behavior, or enforce a checked early rehandshake. A per-session replay window does not deduplicate an application request across *different* sessions. `session.rs:33,155–209`; `identity.rs:26–36`; `crypto/tests/crypto.rs:106–145`. The existing tests also cover round trips, tampering, wrong responder, note-length/padding-related behavior, wrong sender address and repeated initial wire frames. They do not measure privacy against a network observer. Forward secrecy and post-compromise recovery within a long-lived session require their own protocol and threat analysis. [Noise rev. 34, 2018-07-11, §§11.2–11.4 and 14](https://noiseprotocol.org/noise.html)

## 8. A bounded anonymity claim and how to test it

**Proposed ledger claim.** “For eligible shielded transactions between honest, uncompromised wallets, our design aims to hide the participants, price and private action from a computationally bounded third party observing the ledger. Compare histories with the same observable transaction schedule, fee, layout, circuit version, windows, public funding flows, and pattern of public conflicts. The adversary sees all proofs, commitments, ciphertexts and nullifiers generated in each history. It also receives any information legitimately available to the compromised participants in its specified role.” An eventual indistinguishability argument should give negligible guessing advantage under the concrete suite's assumptions. Matching the *actual values* of the commitments or ciphertexts ahead of time invalidates this test. This is a target for a future proof.

**Proposed network claim.** “We aim to reduce linkage between honest accounts' payments and conversations while their devices follow a measured common traffic and synchronization schedule. Nodes learn what their roles expose. A global traffic observer can still infer relationships from timing, availability and side information. We have no demonstrated upper bound on its success for this project.” A single-use reply block enables a reply route without supplying the caller's ordinary return address to the responder. In the inspected reverse-rendezvous demo the peer learns the throwaway address and later receives the long-lived Nym address inside the session. A gateway, directory, RPC endpoint, the peer, or the observer can learn different parts of a transaction; cover on one segment does not conceal application-level identifiers elsewhere. Loopix’s network design relies on mixing and cover, and Nym identifies long sustained flows such as full-chain sync as a weak case with residual correlation. [Nym whitepaper v1.0, 2021-02-26, §4](https://nym.com/nym-whitepaper.pdf) · [Loopix, USENIX Security, Aug 2017](https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/piotrowska) · [Nym developer limitations, 2026-11-17](https://nym.com/docs/developers/limitations)

**Measurement contract.** Before claiming a numerical bound, fix the observer's corruption placement and power. Give it global packet metadata and the mempool. Test passive recording and bounded active delay, replay and selective withholding separately. Include controlled gateways, mix layers, relayers, RPC servers and a contact-directory operator. Hold exogenous workload and prior information constant in equal-prior A/B trials that exchange honest payer, payee or channel partner. Generate all network traces afresh, including wakeups, scan traffic, positive and negative decryptions, callbacks, submissions, cancellations and retries. Equalizing those trace outputs would erase the evidence under test.

**Concrete first experiment, proposed rather than measured.** Give the observer full link-level packet times, lengths and endpoints, all blocks and mempool arrivals, one participant's gateway logs, and the submission relay and scan server logs. Neither challenge device, its keys, the other challenge gateway nor the honest mixing hops are compromised. Start with passive observation. Repeat with both gateways compromised and with bounded active delays as distinct, harder cases. Run each workload at 2, 10 and 100 concurrent honest covered wallets and report actual eligible candidate counts. Set a provisional decision rule before collecting the results, for example an upper 95% confidence bound below 0.05 on excess binary guessing accuracy over 0.5 in the stated equal-prior game. This is a product threshold for this observer under these conditions, not a cryptographic bound. If sparse launch traffic or mobile sleep fails the threshold, publish that limitation for that profile. Padding a ledger with project-controlled transfers cannot supply independent correspondent pairs. Intentional public operator rewards, legacy public history and informed counterparties are outside the private-payment claim.

- Measure honest continuously covered clients, sparse launch traffic, offline recipients, late claims, mobile background suspension, restore and clock outages separately. Report top-1 pair identification, baseline from prior knowledge alone, and classification advantage above random choice in paired experiments, with confidence intervals on held-out devices/sessions. Predeclare the maximum tolerated advantage per deployment scenario. Empirical results bind the tested observers and workloads only. With one plausible pair, public statements about relationship anonymity are unjustified irrespective of proof-system strength.
- Download complete *authenticated* finalized ranges on the same schedule for matching and nonmatching wallets. Verify completeness, inclusion, finality and freshness. Keep Merkle witnesses and spent-state tracking local. A targeted Merkle-path/nullifier/RPC query exposes its subject to the service even through a mixnet; a separate fetch or callback after successful decryption can link the wallet to the record. Prefer identical padded ranges and fixed retry policies, and test battery, cover availability and tail latency on a phone. Never assert a current balance after an incomplete sync. Historical research on wallet receiver timing shows why the joint test matters. [Nym developer limitations, 2026-11-17](https://nym.com/docs/developers/limitations) · [Tramèr, Boneh and Paterson, USENIX Security, Aug 2020](https://www.usenix.org/conference/usenixsecurity20/presentation/tramer)
- Disclose the sender/recipient's own knowledge, published fee split, earlier public chain history, published contact cards, node and gateway roles, authorized view-key disclosures, archived classical ciphertext, observer side information, root-secret compromise and governance changes. The project owner's pseudonym implies no guarantee about a wallet user's anonymity. Application analytics, push tokens, directory requests and support logs are also evidence if present and need an explicit retention and linkage review.

### Who can still learn what

- **Every ledger observer** sees when a transaction appears, its public fee and split, public funding or exits where enabled, and the public version and validity window. A relayer can see submission before inclusion.
- **Both escrow participants** know the agreed price and can recognize the transaction that consumes their shared escrow. They can normally recognize a refund. Keeping the refund's later spend private requires an ordinary nullifier secret held by its owner.
- **A correspondent** knows what was delivered to it. In the current demo it also obtains a reusable identity and, on the reverse-rendezvous path, a long-lived routing address.
- **A gateway or sync service** can observe device availability, request timing and query patterns to the extent visible in its role. The application must account for mobile sleep, retries and backup restoration.
- **A global observer with side information** can make timing and small-population inferences. No project measurement establishes a bound. Old public chain history, device compromise and voluntary disclosure remain usable evidence.

## 9. Phone proving and circuit size

**On-device proving is plausible enough to prototype. This review establishes no handset latency or memory guarantee.** For a two-input/three-output feasibility profile matching the model slot counts, budget test capacity around **0.22 million constraints**, then stress around **0.44 million**. These are workload targets, not a synthesized Anonymum count or an upper bound. The 0.22-million anchor is the arithmetic sum of two independent Sapling Spend circuits and three Output circuits: `2 × 98,777 + 3 × 7,827 = 221,035`. Those upstream counts already include Sapling-specific checks. Anonymum shares some work in a single proof, changes several note types, and adds recovery derivation, tier receipts, time/fee rules and conditional branches. Simply gating a part of an R1CS with a private flag does not remove it from the compiled relation. A twofold stress margin is a planning assumption. [Sapling implementation, tag 0.5.0, tests inspected 19 Nov 2026](https://github.com/zcash/sapling-crypto/blob/0.5.0/src/circuit.rs)

One can cross-check the dominant terms. The Sapling specification counts 1,380 constraints per level with its Pedersen membership construction, or 44,160 for a 32-level path. A two-input circuit using that construction would have 88,320 path constraints before the rest of the relation. Those paths are already in the Spend count above. Synthesize and report separate rows for Merkle paths, ownership/key derivation, commitments/serials, actual authorization binding, amounts and branches, refund derivation, and admission/effect binding. In particular, substituting SHA-256 over a multi-kilobyte effect **inside** the circuit can dominate the entire estimate. Have the runtime digest and the signature authenticate public ciphertext bytes, with explicit equality of proof-bound fields. The shorter digest must never allow modified public effects, a misbound tier, or alteration of refund output fields. [Zcash protocol, Appendix A.3, checked 19 Nov 2026](https://zips.z.cash/protocol/sapling.pdf)

Zcash’s Sapling launch material reports payments constructible in a few seconds with 40 MB of memory, without a comparable phone/device workload in that statement. Mopro’s Samsung S23 Ultra test of an unrelated Anon Aadhaar circuit reports 3.39 seconds for rapidsnark and 33.24 seconds for arkworks on the same device, with witness generation measured separately. Neither is a BLS12-381 Anonymum settlement benchmark. Backend, keys, complete circuit and target phones all matter. [Zcash, 29 Oct 2018](https://z.cash/upgrade/sapling/) · [Mopro v0.3 primary benchmark, checked 19 Nov 2026](https://zkmopro.org/docs/performance/)

**First measurements.** Publish the pinned suite, backend, optimization flags, full constraint counts, witness count, key size and download bytes. On a named low-memory Android, a mid-range Android and the oldest supported iPhone, run the *same complete circuit* for payment, open, decline and refund. Measure cold/warm key load, witness generation, proving, peak resident memory, energy and repeated proofs under thermal load, including OS kills and background suspension. Separately report construction to finality over Nym, restores from only the promised backup, and late-claim inclusion with the real slot grid. Use repeated independent sessions and report sample counts and uncertainty for tail estimates. Proposed initial product gates for discussion: p95 foreground construction within 15 seconds on the nominated mid-range device, zero process kills in the declared stress runs on the lowest supported device, and a published minimum claim lead time derived from measured end-to-end inclusion tails. A remote worker receiving plaintext witnesses changes the privacy model; it cannot silently become the fallback.

## 10. Audit order, effort and cost

**Decision for the owner.** Commission a fixed-scope human design review and a valueless prover/restore spike first. Defer the production audit and ceremony spend until the precise statement, runtime route, two-wallet recovery test and handset measurements pass. Reserve independent reviewers even when the implementation lead is an experienced cryptographer.

## 11. Acceptance fixtures and the next repository pass

**First end-to-end acceptance fixture.** Open with a price of 101 base units. Keep the sender offline and have the recipient **decline with syntactically valid but unusable settlement ciphertext**. Wipe the sender wallet. Restore only the documented backup, synchronize finalized history and identify the exact transaction consuming this escrow's common serial. The restored wallet must compute the 99-unit principal refund, locate it at the correct new position, and actually spend that note. If using the capped reserve in §5, also find and spend the distinct fee rebate even when the recipient **claims** and the sender has no principal refund. A subsequent ordinary transfer incurs its own fee, so spending a 99-unit input and delivering a net 99 units to a third party are distinct tests. Supply a separate fee input for the latter. A one-unit price retires the full principal on refund under round-up; zero principal must never be displayed as spendable money.

| Additional fixture | Required outcome |
|---|---|
| Original sender authorizes an unreadable opening; separate case where a relay changes a signed byte | First may enter consensus but grants no inbox access. Second fails authorization without a state change. Returned funds require an actual included refund. |
| Same escrow, each role, several recognized roots, first-finality race | Every valid resolution presents the same serial; only one finalizes. No provisional receipt opens a paid channel irrevocably. Repeat after a simulated fork rollback and a version migration. |
| Two opens with the same commitment at different positions and two deliveries of a single receipt | Distinct escrow serials and distinct derived refund notes for the separate funded leaves. One request per accepted receipt under the published deduplication policy. No second inbox grant from one burn. |
| Ordinary note after refunded payment | The recipient can recognize the resolution and refund output using the escrow opening. No public later-spend identifier should be computable from those data. Security review must establish this for the selected ordinary key relationship; absence of a match in a handful of test cases does not prove it. |
| Private retirement and fees | Inspect the public ledger, events, state, mempool responses, archives and ordinary wallet RPC. The only per-transaction public debit from the private pool is the common fee. Closed sums reconcile across operator payments and any return to the private pool. |
| Restart and identity | Two devices restore and use an invitation concurrently. Crash and restore a transport session. Fail closed or initiate a fresh session as specified, with no duplicate paid admission and no same-key nonce reuse. Unknown senders must be able to complete legitimate first contact without a clear sender hint. |
| Sparse network / global observer | Compare matched and unmatched scan traffic and behavioral traces on realistic phones. If a contacted phone's reply or fetch identifies it, change the operating profile or narrow the public claim. Do not advertise a guarantee measured only in a busy lab. |

**Independent finite check recorded on 19 November 2026.** For every integer price from 0 through 1,000, reserve ceiling from 0 through 32 and fee from 0 through the chosen ceiling, I enumerated both settlement outcomes in §5. **1,123,122 value equations passed.** I also checked that select valid boundary cases sum to exactly the maximum unsigned 64-bit amount, and that a larger-than-reserve fee and overflow funding are rejected by the independent arithmetic model. The test examines the proposed fee equations, not the reported Rust model, input authorization, proof soundness, source code or transaction delivery. Essential reconstruction of the check:

```text
for P = 0..1000, C = 0..32, F = 0..C (all endpoints inclusive):
    k = (P div 100) + integer(P mod 100 != 0)
    Q = C - F
    assert P + Q + 0 + F == P + C            # claim
    assert (P - k) + Q + k + F == P + C     # refund
    assert all payout/retirement amounts are nonnegative
```

**Reproducibility.** The source copy used for the root tests matches the pinned commit in every Rust source and Cargo input inspected. Test counts by executable were 2 + 59 in core, 1 + 10 + 8 + 6 in messaging crypto, and 1 + 3 + 40 + 1 in the shielded model. The randomized model suite passed; its input space and the independent fee enumeration above are different evidence. In the model's reported two-wallet fixture, the recipient receives the escrow plaintext directly through the test harness, not by discovering and decrypting an actual stranger contact on a second device. Re-run the new recovery and privacy tests at a future immutable release commit. The separate transparent pallet command `cargo test --offline --locked -p pallet-anonymum` also passed 57 tests. It does not contain the proposed shielded verifier. The project repository was read only.

**Release decision.** Prioritize independent human review of the selected note/key relationships and mandatory payouts, then a complete valueless prover and two-wallet restore demonstration. The truthful public statement today is: *Anonymum is developing shielded payments and private contact requests. The cryptography, phone performance and resistance to combined ledger and network observation have not yet been demonstrated in this project.*
